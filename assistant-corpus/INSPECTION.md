## Concept granularity decisions

### Portfolio (`portfolio/`)

**Chosen:** one case overview concept, one concept per supporting block (five prose + one architecture), plus one article catalog entry.

| Alternative considered                   | Why not chosen                                                                                                  |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Single case-level concept only           | Loses block-level provenance anchors (`#b04`) and mixes unrelated categories (System, Constraints, Decisions)   |
| One concept per sentence / paragraph     | Fragments contracts and gutter notes that belong with their block; mirrors presentation rails too literally     |
| Merge article catalog into case overview | Catalog metadata is a different source shape (external URL, tags, `relatedProjectSlug`) with its own `resource` |

**Boundary feel:** Natural. Supporting-case blocks are already authored as knowledge units with stable ids (`b01`–`b06`). Architecture block becomes a summary concept with an ecosystem link — canvas coordinates and React Flow state are intentionally omitted.

### Repository runbook (`repo/`)

**Chosen:** five semantic concepts — overview, prerequisites, operator ladder (Workflow section), automation/policy, troubleshooting (+ merge policy table).

| Alternative considered                     | Why not chosen                                                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| One whole-document concept                 | Hides section boundaries useful for provenance and cross-links; 270 lines is readable but coarse                             |
| One concept per `##` heading (11 concepts) | Several headings are reference tables or naming indexes, not standalone knowledge; would optimize for retrieval-sized chunks |
| Split operator steps 1–6 individually      | Steps share one routing narrative; splitting would duplicate classifier/investigator/maintainer context                      |

**Boundary feel:** Mostly natural. `## Overview` and `## Prerequisites` are clean cuts. `## Workflow` is the richest section and remains one concept because the parked-draft lifecycle and step sequence are one operational story. Troubleshooting and merge-policy tables are combined so policy tiers stay adjacent to stop conditions.

### Published writing (`writing/`)

**Chosen:** metadata concept (YAML frontmatter fields) + single narrative concept for the full article body (HTML comments stripped).

| Alternative considered                       | Why not chosen                                                                                                                           |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| One whole-file concept including frontmatter | Mixes editorial sync metadata with reader-facing narrative                                                                               |
| One concept per `##` section (6+ concepts)   | Field report sections are sequential argument, not independent reference pages; splitting would favor chunk retrieval over authored flow |
| Preserve HTML comments in body               | Comments are drafting notes for editorial workflow, not published knowledge                                                              |

**Boundary feel:** Natural for this article shape. First-person narrative and incident detail stay intact in one concept; catalog and Notion/DEV sync fields are inspectable separately.

## Architecture direction recommendation

**Proceed** with OKF as the normalization layer and run a **second experiment** later if figure-bearing portfolio content (`CaseFigure` + inventory `source`) or ecosystem graph normalization becomes the primary open question.

This bundle confirms:

1. Multi-source producers can stay isolated (portfolio does not read fixtures).
2. Deterministic fixture pinning works for repo and DEV inputs.
3. Concept granularity can follow source semantics without pre-committing retrieval chunk sizes.

Retrieval-unit derivation, embeddings, and assistant runtime remain out of scope until this inspectable corpus is reviewed.
